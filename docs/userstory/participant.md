# 参加者(旅行者)側の価値

根拠: [ideas.md](../ideas.md) 4章(P1)、5章(エピック A/C/D/G/H)、5.5、[design.md](../design.md) 3章。
凡例: 「事実」=docsに記載、「提案/仮説」=本書での補足・docs上も未検証。

## ペルソナ(ideas.md P1)

**ミサキ(29歳、会社員、都市在住)**: 日常はオンライン中心でリアルな人間関係が薄いと感じる。観光そのものより、旅先で誰かと話し、一緒に何かをしたい。マッチングアプリは「目的が重くなる」ので苦手で、「ゆるく会える」場を探している。知らない人と会う不安がある。

補足ペルソナ(タイプ分け、ideas.md 3章の仮説): 定着型(同じ地域を何度も回る)/探索型(複数都市を回り、自分に合う街を探す)。

## ユーザストーリ

### US-P1 出会いのあるキャンペーンを選ぶ
- ストーリー: ひとり旅の旅行者として、行き先を選ぶときに「出会いがあるキャンペーン」だと分かりたい。なぜなら、観光だけの旅行と区別して選びたいから。(A-1 / G-1)
- 体験価値: 旅先選びの時点で「誰かと会える旅」だと期待が持てる。
- 受け入れ条件: 全国のキャンペーン一覧(ランディングページ)から、出会い軸のキャンペーンが識別できる。
- 関連画面/機能: ランディングページ(新規)、キャンペーン一覧、「行きたい」(旅先の保存)

### US-P2 探して、日程を入れる
- ストーリー: 旅行者として、地方・テーマ・季節で旅先を探し、日程と人数を入れたい。なぜなら、同じ日に旅する人を探したいから。(G-2〜G-5, H-1, H-3)
- 体験価値: 少ない手間で「自分の旅」に条件が決まる。日程は幅で入れられる(G-4)。
- 受け入れ条件: 日程(開始・終了、幅)、人数、グループ構成を入力・保存できる。
- 関連画面/機能: 旅程入力(Trip/Party、新規)、旅先の保存

### US-P3 人の気配で行き先を決める
- ストーリー: 旅行者として、各旅先で同じ日程に参加予定の人数を知りたい。なぜなら、人の気配で行き先を選びたいから。(H-2)
- 体験価値: 「行けば誰かがいる」安心感。
- 受け入れ条件(提案): 人が少ない時期は人数でなく「新しい参加者が現れたら通知」を前面に出す(ideas.md 5.6の注意に対応)。
- 関連画面/機能: 参加予定人数の表示(新規)、通知

### US-P4 リンクから、入力済みで始める
- ストーリー: 旅行者として、自治体サイトや旅行サイトのリンクから来たとき、地方・日程が入力済みの状態で始めたい。なぜなら、同じ入力を繰り返したくないから。(H-4)
- 体験価値: 入口Bからの迷いのない着地。
- 受け入れ条件: リンクの条件は個人情報を含まず、地方と日程に限る。
- 関連画面/機能: ランディングページ(入口B)

### US-P5 ゆるく、安心して一緒に回る
- ストーリー: 旅行者として、プロフィールの公開項目を自分で選び、気に入った人・グループに同行の希望を出したい。なぜなら、初対面でも安心して、共通の目的(ラリー)で自然に話したいから。(A-4, A-5, G-6〜G-8)
- 体験価値: 重い恋愛目的ではなく「旅の同行者探し」としてゆるくつながる。ラリー(スタンプ)が共通の話題になる。
- 受け入れ条件(叩き台、ideas.md 5.5): 双方の承諾がそろうまで本名・連絡先は見せない/公開項目は利用者が選ぶ/18歳未満は利用不可/通報・ブロックはいつでも可。
- 関連画面/機能: 同行候補一覧、プロフィール、同行の希望・承諾(CompanionRequest/Match)、スタンプ・ポイント獲得、スポット、地図(既存流用)
- 備考: 規制確認前のため第2段階の扱い(design.md 3.1)。

### US-P6 断られても傷つきにくい / 成立後の約束
- ストーリー: 旅行者として、承諾・断りを選べ、断る際も相手を傷つけにくい形にしたい。成立後は待ち合わせ・日程変更・辞退を伝えたい。なぜなら、すっぽかしや気まずさを避けたいから。(G-9〜G-13)
- 体験価値: 無理のない関係づくり。連絡は双方承諾後のみ。
- 関連画面/機能: 成立後チャット(新規、モック可)、辞退・日程変更

### US-P7 安全に使い続ける
- ストーリー: 旅行者として、通報・ブロックができ、待ち合わせは公共の場所を勧められたい。なぜなら、初対面の人と移動するのは不安だから。(F-2, F-5, G-15)
- 体験価値: 不安の軽減。
- 関連画面/機能: 通報・ブロック、本人確認(最低限)、合流の確認(任意)

### US-P8 振り返り、また行く理由を持つ
- ストーリー: 旅行者として、出会った人や訪れた場所の記録(写真・スタンプ・メモ)を残し、再訪や回数に応じた特典・称号がほしい。なぜなら、自分の物語として積み上げ、通う意味を感じたいから。(C-2〜C-5)
- 体験価値: 旅が「その場で完結」しない。人・記録・特典が再訪の理由になる(ideas.md 2章の6条件)。
- 関連画面/機能: マイページ、獲得履歴、写真投稿、SNS共有、特典、リセット(周回)、通知/LINE

### US-P9 連絡は、お互いが望む時だけ
- ストーリー: 旅行者として、旅の後も、双方が望む場合だけ連絡手段を持ちたい。なぜなら、一期一会も継続もどちらも選べるようにしたいから。(C-1)
- 受け入れ条件: 連絡先交換は双方同意時のみ(F-4)。
- 備考: 利用者間連絡は規制の該当性に関わる(ideas.md 7.5)。

### US-P10 複数の街を見比べる(探索型)
- ストーリー: 探索型の旅行者として、複数都市のラリーを1アカウントで管理し、体験を同じ形式で見比べたい。なぜなら、自分に合う街を選びたいから。(D-1〜D-3)
- 備考: 既存はキャンペーンごとにアカウントが分かれている可能性(推定)。共通識別は未決。優先度 S/C。

### US-P11 少人数イベントに一人で参加
- ストーリー: 旅行者として、ひとりでも参加できる少人数の集合型イベントに申し込みたい。なぜなら、マッチングより参加しやすいから。(A-6)
- 備考: 優先度はC(将来)だが design.md 3.1 では第1段階。矛盾として確認事項に記載。

## 価値の要約(スライド1枚用)

1. 観光が目的ではなく「誰かとゆるく出会える旅」: 旅先選びの時点から出会いの見込みがある。
2. ラリー(スタンプ・スポット)が、初対面でも話せる共通の目的になる。
3. 公開範囲は自分で選び、双方の承諾後にしか連絡先を出さない安心設計。
4. 旅の記録・出会い・特典が積み上がり、「また行く理由」が生まれる。
5. リンク1つで地方・日程入力済みから始められる手軽さ。

## 確認事項(このファイル固有)

- A-6(集合型イベント)の優先度 C と、design.md 3.1 の第1段階配置の不一致。
- C-1(連絡手段)も第1段階に含まれるが、利用者間連絡は規制確認が前提(7.5)で、第1段階の「規制リスクが低い形」との整合が曖昧。
- G-9 は「旅行者として」書かれているが、受信側の立場(承諾する側)の話である。
- ペルソナの性別・年齢の属性は仮説(ideas.md 4章)で、ユーザー調査はしていない。
