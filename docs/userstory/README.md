## サービス概要

既存のスタンプラリー型キャンペーン基盤(Raund。キャンペーン単位のマルチテナントWebアプリで、スタンプ/ポイント、スポット、特典、通知、LINE連携を持つ)を発展させ、観光ではなく**出会い・つながりを主目的**に置く「旅の同行者探し」型の観光ラリーにする。旅行者には、旅をきっかけに「どこかの誰か」と出会う体験を、自治体には、出会いの場として「選ばれる」動機と個人を特定しない成果指標を、運営者には自治体を主軸とした収益構造を提供する。移住は希望者向けの付加要素で、恋愛は前面に出さない(規制と誤解の回避)。

## 各登場人物の価値(要点)

- 参加者: 観光だけでなく「誰かとゆるく出会える旅」。ラリーが共通の話題、公開範囲は自分で選べ、双方承諾後にだけ連絡。記録・特典が再訪の理由に。
- 自治体: 関係人口を生む場として選ばれる。テンプレートで短時間に立ち上げ、個人非特定の指標で成果を説明、送客リンクで集客。
- サービスプロバイダ: 主軸は自治体の運営費、副に事業者の協賛・送客手数料。利用者課金は初期は避ける。既存機能を流用し、安全・規制に配慮して段階的に拡張。
- 地元の人: その場限りの接客が再訪につながり、負担は自分で決める。断る権利がある。
- 地元事業者: スポット・特典としての来客導線と成果確認(提案)。

## 確認事項(docs間の矛盾・曖昧点)

1. **MVP範囲の不一致**: design.md 3.1 は第1段階で相乗りマッチングを避け(第2段階=規制確認後)、output.md 4.3/4.4 のデモは同行候補・希望承諾(優先1〜4)が中心。デモと設計段階の整合が未整理。
2. **A-6 集合型イベント**: ideas.md では優先度C(将来)、design.md 3.1 では第1段階。
3. **C-1 連絡手段**: 第1段階に含まれるが、利用者間連絡は規制の該当性に関わる(ideas.md 7.5)。
4. **競技ルールとの衝突**: rule.md は「ログイン・認証不要、外部API・外部サービスへの実行時依存禁止、Google Maps等は不可」。docs の本人確認、チャット、LINE連携、Giftee/PayPay 連携は競技スコープではモック化が前提(output.md 4.2)。rule.md 優先。
5. **個人情報**: rule.md は実在個人情報の利用を禁止。プロフィール・同行機能のデモは、sample-data またはダミーデータを使う必要がある。
6. **自治体の位置づけ**: 主な顧客(design.md 1.2「決定」)だが、顧客・契約形態・価格帯は未確認(ideas.md 7.6)。
7. **ペルソナP3** は「観光・移住担当」だが、移住は前面に出さない方針(design.md 1.2)。
8. **ストーリー主語**: G-9 は「旅行者として」だが承諾側の話。
9. **名称**: 「相乗り」「同行」「あいのり」が混在し、恋愛連想を避ける名称は未決(ideas.md 5.5)。
10. **提出先・評価・期限**は未確認(output.md 9章)。
11. 既存サイトの情報はログイン前の静的解析に基づく推定を含む(overview.md、scratch.md 0章)。
