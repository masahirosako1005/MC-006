# サービスプロバイダ(運営者)側の価値とマネタイズ

根拠: [ideas.md](../ideas.md) 4章(P4)、エピック F・H-5、7.5、7.6、[design.md](../design.md) 1.2・1.3・5章、[scratch.md](../scratch.md)。
重要: 収益源の候補は docs 上も**ディスカッションの見立て**(市場調査・顧客ヒアリング未実施、ideas.md 7.6 注意書き)。金額・単価・数値は docs に無いため本書でも記載しない。「提案」は本書での整理。

## ペルソナ(ideas.md P4)

**サービス運営者(われわれ)**: キャンペーンを作り、運用し、効果を測る。利用者の安全と信頼を守る責任がある。既存サービス(Raund。スタンプラリー運営のマルチテナントWebアプリ)を発展させる立場(事実: overview.md)。

## ユーザストーリ

### US-S1 安全と信頼を段階的に担保する
- ストーリー: 運営者として、出会い機能を使う人の本人確認を段階的に求めたい。なぜなら、安全を担保しないと参加者が離れるから。(F-1)
- 体験価値: 信頼されるサービスとして継続できる。
- 関連機能: 本人確認(新規、水準は未決)、年齢確認(18歳未満の排除)

### US-S2 通報・ブロックと利用制限
- ストーリー: 運営者として、通報・ブロックの受付と、繰り返す人の利用制限をしたい。なぜなら、迷惑行為を抑えたいから。(F-2, F-3)
- 関連機能: 通報・ブロック・利用制限の運用画面(新規)。運用の担い手は未決。

### US-S3 同意のある時だけ連絡先を出す
- ストーリー: 運営者として、連絡先の交換を双方の同意があるときに限りたい。なぜなら、プライバシーと規制リスクを下げたいから。(F-4)
- 関連機能: 同意管理(Consent)

### US-S4 規制を確認して、安全側で小さく始める
- ストーリー: 運営者として、恋愛目的を含める場合の法的要件を事前に確認し、「旅の同行者探し」に位置づけを揃えたい。なぜなら、出会い系サイト規制法・旅行業法の該当リスクを避けたいから。(F-6)
- 体験価値(事業継続性): 規制リスクの低い形で価値を検証できる。
- 関連: 第1段階(集合型イベント等)→第2段階(同行、規制確認後)(design.md 3.1)。

### US-S5 集客の効果を流入元別に見る
- ストーリー: 運営者として、流入元別に、登録や相乗り成立までの動きを見たい。なぜなら、投資すべき導線を判断したいから。(H-5)
- 関連機能: 流入元別計測(既存タグの拡張。使える状態かは未確認)

### US-S6 既存資産を活かして拡張する(提案)
- ストーリー: 運営者として、既存のラリー・スポット・特典・通知・LINE連携・計測を流用して新機能を足したい。なぜなら、新規開発の範囲を絞りたいから。
- 備考: scratch.md 2.4 は「新規」が多く、新しい領域(利用者どうしの関係)を作ることになると評価している。

## マネタイズポイント

### 事実(docs記載)
| 項目 | 内容 | 出典 |
|---|---|---|
| 主軸 | 自治体のキャンペーン運営費(観光振興・移住定住・関係人口の予算) | ideas.md 7.6 |
| 副 | 地元事業者の協賛・送客手数料(店、宿、体験事業者、交通会社) | ideas.md 7.6 |
| 当面扱わない | 出会い機能への課金(規制リスク) | ideas.md 7.6 / design.md 1.3 |
| 初期は避ける | 利用者課金(参加者が少ない段階の障壁) | ideas.md 7.6 |
| 既存の課金関連機能 | チケット・コース購入(`/products/tickets`、決済サービスは未特定)、EC機能フラグ | overview.md |

docs内の相性評価: 運営費 ◎、協賛・送客手数料 ○、企業協賛 △、有料イベント枠 △、出会い機能課金 ✕。

### 導入順序(docs記載の案)
1. 少数自治体で、イベント型・参加型の最小形を運営費をもらって試行
2. 地元事業者の協賛・送客手数料を追加し、自治体予算への依存を下げる
3. 利用者が増えたら有料イベント枠など利用者課金を試す
4. 複数都市横断機能を提供し、探索型を受け入れる

### コスト構造の要点(docs記載の範囲)
- 運用コスト: 通報の確認、本人確認の審査、協力者の承認(scratch.md 4章)。
- 外部サービス費用: 本人確認等の外部サービス利用(scratch.md 2.3。費用は未見積)。
- 自治体営業の構造: 単年度予算、入札・プロポーザル、営業サイクルが長い、1件あたり金額が大きくない(多数自治体への横展開が必要)、担当者異動で途切れやすい(ideas.md 7.6)。

### 提案・仮説(docs外、本書の補足。検証は未実施)
- 課金モデル案: 自治体向けは「キャンペーン単位の導入費+運用費」の構成にし、成果指標レポートを成果物に含める。単価は未設定。
- 送客手数料は、地元店が受けた来客・特典利用の計測結果に連動させる案(docsは「来客の成果を示せることが条件」と記載。連動の仕組みは本書の提案)。
- 拡張性: キャンペーン単位のフラグ・テンプレートで横展開しやすい(scratch.md 1.6の推定に基づく仮説)。個人を特定しない集計を自治体比較・事業者向けレポートに使う案は本書の提案。

## 価値の要約(スライド1枚用)

1. 主軸収益は自治体のキャンペーン運営費。成果指標(個人非特定の集計)を価値として提供する。
2. 地元事業者の協賛・送客手数料を副収益にし、自治体予算の途切れに備える。
3. 利用者課金は初期は避け、出会い機能への課金は規制リスクのため行わない。
4. 既存のラリー・特典・通知・LINE・計測を流用し、追加開発を「利用者どうしの関係」領域に集中できる。
5. 規制・安全に配慮し、段階的(第1→第3段階)に拡張。多自治体への横展開と複数都市横断で拡張性。
