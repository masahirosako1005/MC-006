### 2.2 全体所見

- 本線の API は共通ラッパー `route()`(`app/src/lib/api-route.ts`)を通り、Origin 検査・`Content-Type: application/json` 必須・64KB 上限・未知クエリの拒否・ID 形式検査が一貫して効いている。グループ配下の資源は `assertGroupAccess` と `assertInGroup` で所有関係を検査しており、**IDOR の実例は見つからなかった**。
- 一方、本線の外にある **`/api/v2/[...path]`(スタンプラリーのミラー API)は共通ラッパーを通らず**、CSRF 対策・本文サイズ上限・レート制限・入力検証が欠けている(SEC-002)。
- 擬似認証は設計上の仕様だが、**`DEMO_TOOLS=off` でも Cookie を書けば誰にでも成り済ませる**。無効化スイッチが「本番相当の守り」と誤認されないよう明記が必要(SEC-001)。
- 統計(自治体)・インサイト(事業者)の少数セル抑制は、1 レスポンス内では補完秘匿まで実装されているが、**期間・地方・公式フィルタを変えた複数回の問い合わせを突合する差分攻撃**で抑制セルが復元できる(SEC-004)。
- 長文入力に対する禁止語の正規表現(メールアドレス)が二次関数的に遅く、上限検査の前に禁止語検査が走る経路(再企画)で **約 2 秒/リクエストの同期 CPU 消費**を確認した(SEC-003)。

### 2.3 最優先で直すべき上位 3 件

1. **SEC-002(High)** `/api/v2/*` を `route()` 配下に移すか同等の入口検査(Origin・Content-Type・サイズ・レート制限)を付け、`inquiries` の無制限蓄積を止める。
2. **SEC-001(High)** 本番化では署名付きセッション(または IdP)に置き換える。デモ中は `DEMO_TOOLS=off` が成り済ましを防がないことを README・デモ手順に明記する。
3. **SEC-003(Medium)** 再企画 API の `name`/`destination` に長さ上限を付け(LIMITS を再利用)、禁止語検査の前に長さ検査を行う共通ルールにする。あわせてメールの正規表現を線形化する。

各指摘の「分類」は CWE と OWASP Top 10(2021)。「場所」は `ファイル:行`。コード抜粋は最小限とし、秘密・個人情報は記載しない。

### SEC-001 デモ無効化(`DEMO_TOOLS=off`)でも Cookie 偽装による任意ユーザー成り済ましが可能

- 重大度: **High**(本番化時は Critical) / 確度: Confirmed
- 分類: CWE-287(不適切な認証)、CWE-565(検証なしの Cookie 依存) / A07 Identification and Authentication Failures
- 場所: `app/src/lib/current-user.ts:19-26`、`app/src/lib/api-route.ts:95-99`、`app/src/lib/demo-handlers.ts:12,31-39`
- 説明: ユーザー識別は Cookie `demoUser=<id>` の値をそのまま信用する。`isId("u", v)` の形式検査と存在確認だけで、署名・有効期限・発行元の検証がない。`DEMO_TOOLS=off` は `POST /api/demo/me`(切替 API)を 404 にするだけで、`currentUser()` の Cookie 信用は変わらない。
- 再現・根拠: ブラウザの開発者ツールで `document.cookie="demoUser=u-003"` のように自治体・事業者ロールの ID を設定すると、`/api/stats`・`/api/insights`・幹事操作など当該ロールの全操作ができる。`/api/demo/users` が ID を一覧し、ID は連番(`u-001`…)なので推測も容易。
- 影響: デモ環境では仕様どおり(利用者が自由に視点を切り替える)。しかし「`DEMO_TOOLS=off` にすれば他人の操作ができない」という誤認が生じやすい。本番化でこの方式が残ると、全ロール・全ユーザーの成り済まし(IDOR の全面化)になる。
- 推奨対策:
  1. README・デモ手順に「`DEMO_TOOLS=off` は UI/API の切替を隠すだけで、Cookie を書けば誰にでもなれる」と明記する。
  2. 本番化では、サーバー署名付きセッション(HMAC/JWT、`Secure; HttpOnly; SameSite=Lax`、短寿命+更新)または既存 IdP に置き換え、`currentUser()` の入口を 1 箇所に保ったまま差し替える。
  3. `DEMO_TOOLS=off` のとき `currentUser()` も Cookie を無視して既定ユーザー固定にする(デモ限定の暫定策)。
- 区分: デモ仕様(第 5 章 D-1)の延長だが、無効化スイッチの意味の誤認は現時点の問題として扱う。

### SEC-002 `/api/v2/[...path]` が共通ラッパーを通らず、CSRF・サイズ上限・レート制限・入力検証が欠ける

- 重大度: **High** / 確度: Confirmed
- 分類: CWE-352(CSRF)、CWE-770(制限のない資源割当)、CWE-20(不適切な入力検証) / A01 Broken Access Control、A04 Insecure Design
- 場所: `app/src/app/api/v2/[...path]/route.ts:65-86`、`app/src/lib/server-store.ts:27-44,82`
- 説明: 本線の API は `route()` で Origin 検査・`application/json` 必須・64KB 上限を受けるが、`/api/v2` は独自実装で `req.json().catch(() => ({}))` を直接呼ぶ。
  - `POST /api/v2/user/reset`(周回リセット・スタンプ全消去)、`POST /api/v2/user/stamps`(合言葉で押印)、`POST /api/v2/inquiries` は、他サイトから `fetch(url, {method:"POST", mode:"no-cors", headers:{"Content-Type":"text/plain"}, body:'{"email":"a@b","message":"x"}'})` のような「単純リクエスト」で発火する。Cookie 不要なので SameSite の保護も関係しない。
  - `inquiries` は `state().inquiries.push(...)` で**無制限に蓄積**され、件数上限・レート制限・本文サイズ上限(`message` は 2000 文字だが本文全体の上限なし)がない。
  - 本文が JSON の `null`/数値の場合、`body.keyword` でプロパティ参照が TypeError になり、未処理の 500 になる(`route.ts:69`)。
  - 投稿されたメールアドレス・本文(個人情報になり得る)がプロセスメモリに保持される(永続化はしない)。
- 影響: 第三者サイトからの訪問者端末を踏み台にしたスタンプ状態の破壊(デモの進行妨害)、問い合わせのスパム・メモリ消費によるサービス停止、問い合わせ内容の保持。
- 推奨対策:
  1. `/api/v2` のハンドラを `route({ auth: "none" })` 配下に移し、入口検査を共通化する(最小限なら `guardMutating` 相当の Origin・Content-Type・`content-length` 検査を追加)。
  2. `inquiries` に件数上限(例: 100 件、超過時は古いものを捨てる)と `checkRate` 相当の制限を付ける。保存する場合は本文を保持しない(件数のみ)か、デモでは受理のみで破棄する。
  3. `body` が object であることを確認してからプロパティを読む。
- 区分: デモ仕様(本番 API の形を再現するローカル用モック)だが、現状でも悪用可能。

### SEC-003 再企画 API の長さ無制限の文字列に対する禁止語正規表現で、同期 CPU を約 2 秒/件消費できる(ReDoS 相当)

- 重大度: **Medium** / 確度: Confirmed(概念実証あり)
- 分類: CWE-1333(非効率な正規表現の複雑性)、CWE-400(制御されない資源消費) / A05 Security Misconfiguration(入力長の未制限)
- 場所: `app/src/features/groups/lifecycle/handlers.ts:46-47`(`name`・`destination` が `v.string({ optional: true })` で上限なし)、`app/src/features/groups/lifecycle/replan.ts:64-68`(長さ検査より先に `assertTextAllowed`)、`app/src/features/safety/text/dictionary.json:6`(`contact.email`)、`app/src/features/safety/text/check-text.ts:47`(`matchAll`)
- 説明: 本文全体は 64KB で止まるが、`replan` の `name`/`destination` は 1 項目で約 6 万文字まで通る。`replan()` は `validateCreateGroupInput`(30/40 文字上限)より前に `assertTextAllowed(name, "group_name")` を実行するため、全辞書の正規表現が 6 万文字に対して走る。`contact.email` の `[a-z0-9._%+-]+@...` は `@` を含まない長い英数字列に対し、開始位置ごとに末尾まで貪欲に消費して戻るため O(n²) になる。
- 再現・根拠: 辞書の正規表現をそのまま用いた読み取り専用の計測(Node 24)で、`"a".repeat(n)` に対し n=10,000 で 61ms、30,000 で 537ms、60,000 で **1,912ms**(他 3 本の連絡先系パターンは 1ms 未満)。到達条件は「中止済みグループの幹事」だが、任意ユーザーがグループ作成→中止→再企画で満たせる(SEC-001 により実質誰でも)。Node は単一スレッドのため、同時に数十件送るとイベントループが秒単位で停止する。
- 影響: サービスの応答停止(DoS)。
- 推奨対策:
  1. `replanHandler` の `name` に `LIMITS.GROUP_NAME`、`destination` に `LIMITS.DESTINATION` を適用する(1 行の修正)。
  2. 「長さ検査 → 禁止語検査」の順序を共通ルールにし、`assertTextAllowed` 側でも入力長の安全弁(例: 2,000 コードポイント超は即 `invalid_input`)を置く。
  3. `contact.email` を `(?<![a-z0-9._%+-])[a-z0-9._%+-]{1,64}@[a-z0-9-]{1,63}(\.[a-z0-9-]{1,63}){0,8}\.[a-z]{2,24}` のように各部に上限を付け、先読み/後読みで開始位置を限定する。
- 区分: 現時点の問題。

### SEC-004 統計・インサイトの少数セル抑制が、フィルタを変えた複数問い合わせの突合(差分攻撃)で迂回できる

- 重大度: **Medium**(本番データでは High 相当) / 確度: Confirmed(コード上の論理)
- 分類: CWE-359(個人情報の露出)、CWE-201(送信データによる情報露出) / A01 Broken Access Control(意図した秘匿の迂回)
- 場所: `app/src/features/stats/query.ts:14-60`(`from`/`to`/`region`/`official`)、`app/src/features/stats/metrics.ts:92-95,228-250`(フィルタ後に独立して抑制)、`app/src/features/stats/privacy.ts:16-26`(補完秘匿は 1 配列内のみ)、`app/src/features/insights/query.ts:9-22`(`region` 単体指定)、`app/src/features/insights/forecast.ts:107-123`(エリア別の補完秘匿)
- 説明: 少数セル規則(k=5、`MIN_CELL_COUNT`)は各レスポンスの各セルに独立に適用される。`suppressBreakdown` は同一配列で抑制セルが 1 つのときに最小の別セルも隠す(補完秘匿)が、**別の問い合わせで得た値**との整合までは制御しない。
  - 地方: `GET /api/stats`(全地方)の `summary.groupsCreated` と、`?region=r-x` を地方ごとに呼んだ値の差で、`regionTable` で `few` になっている地方の実数が復元できる(非少数の地方は `region=` 単体指定で実数が返るため、補完秘匿が無効化される)。
  - 期間: `from/to` は月単位で 12 か月まで任意。`[1 月〜3 月]` − `[1 月〜2 月]` = 3 月の実数となり、`timeSeries` で `few` の月も復元できる。
  - 公式: `official=all` − `official=official` = `general` の実数。年代帯(`ageBands`)や中止理由の内訳にも同じ差分が適用できる。
  - インサイト: `region` 単体の `weeks[].byAge`・`plannedByCertainty` と全体の差で、`areaTable` で `few` のエリアの週別人数(年代別)が復元できる。
- 再現・根拠: 上記はいずれも許可されたクエリの組合せのみで成立し、認可の追加条件はない。デモデータは合成だが、ロジックは本番でも同じ。
- 影響: 自治体・事業者が「少人数の参加者層(年代帯)」を地方×月単位で特定できる。参加者が数人の小規模地域では個人の再識別に近づく。
- 推奨対策(いずれか、または併用):
  1. **固定の集計粒度**: 問い合わせ可能な期間・地方の組合せをあらかじめ決めた区画(例: 直近 3 か月固定、地方は「全体」のみ)に限定し、任意の範囲差分を作れなくする。
  2. **決定的ノイズ**: 同じセルには常に同じ丸め(例: 5 の倍数への丸め、または seed 固定のランダム化応答)を適用し、差分で実数が出ないようにする。
  3. **問い合わせ間の整合**: 単体 `region=` の応答にも全体表と同じ補完秘匿フラグを適用する(全体表で `few`/補完秘匿された地方は、単体指定でも `few` を返す)。期間も同様に、月別が `few` の月を含む範囲の合計は丸める。
  4. 統計の設計書(12・13)に差分攻撃の脅威モデルを追記する。
- 区分: 本番化時の必須対応。デモでも「少数セルを守っている」という説明と整合しないため、少なくとも制約として明記する。

### SEC-012 セキュリティヘッダーの不足(CSP・Permissions-Policy・HSTS)と、リバースプロキシ配下での Origin 検査

## 7. 良好な点(実装されている防御)

- **共通入口** `route()`: Origin/Host 検査、`application/json` 必須、`content-length` と実本文の 64KB 二重検査、未知クエリの拒否、`requestId` 付きの一様なエラー、`Cache-Control: no-store`・`nosniff`。
- **ID の形式検査**(`^<prefix>-\d{3,8}$`)をパス・本文・クエリで統一し、形式不正は存在を漏らさず 404。
- **検証 DSL**(`lib/validation.ts`): NFC 正規化、制御文字・不可視文字の除去、コードポイント長、行数、列挙、配列の一意性、`hasOwnProperty` による安全なオブジェクト解釈。
- **アクセス制御の一貫性**: `assertGroupAccess` が非公開グループやブロック関係を 404 で隠し、幹事判定を二重(メンバー行の role と `organizerId`)で行う。申請・費用・プラン・チャットの全サブ資源で `assertInGroup`。
- **招待コード**: `node:crypto.randomInt` による 32 文字種×10 桁(約 50 ビット)、7 日 TTL、再発行で失効、DTO から常に除去。
- **禁止表現**: NFKC・小文字化・かな統一・漢数字変換・記号除去(`squeezed`)した上で辞書照合し、文脈別に deny/review を切替。費用メモには決済・連絡先誘導の追加ガード。
- **プライバシー**: 性別・年齢クエリの拒否、年代の粗粒度化(3 区分)、少数セル規則 k=5 と 1 表内の補完秘匿、メンバー概要の 4 人未満非表示、スタンプの合言葉を公開 DTO から除去、集計生成スクリプトの識別子混入検査(`checkInsightOutput`)。
- **並行制御**: プラン・費用の `baseVersion`、ライフサイクルの `revision`、`tx()` による原子性。
- **レート制限**: チャット・申請・通報・ブロック・プロフィール・グループ作成に固定ウィンドウ制限。
- **ヘッダー**: `X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`。
- **外部依存なし**: CDN・外部画像・外部 API 呼び出しがなく、地図・画像は同梱。
- **試験**: 入口検査(415/403/413/400)、通報・可視性、禁止語、k 匿名化の単体試験が存在。

## 9. 制約・限界と推奨する次の一手

### 9.1 制約・限界

- **LLM ベース SAST の限界**: ソースの読解に基づく検査であり、見落とし(偽陰性)と誤検知(偽陽性)の両方があり得る。実行時のフレームワーク挙動(Next.js の `cacheComponents`、ルーティング、ミドルウェア不在時の静的配信)は検証していない。
- **動的検査未実施**: DAST・ペネトレーションテスト・ファジングは行っていない。SEC-002/SEC-004/SEC-006 は実機でのリクエスト再現を行わず、コードの論理で確認した(SEC-003 のみ正規表現の計算量を計測)。
- **検証できなかった箇所**: `sample-data/*.csv` の内容(読まない方針)—SEC-011 の値の実在性は未確認。`.env*` の有無(Git 管理外、名称検索のみ)。Next.js 本体・Mantine の既知脆弱性は `npm audit` の範囲に限る。本番相当のデプロイ構成(リバースプロキシ・TLS・ヘッダー付与)は対象外。
- **スコープ外**: ビジネスロジックの正当性(金額計算・遷移規則)はセキュリティ観点でのみ確認。

## 付録: 重大度・確度の基準

| 重大度 | 基準 |
| --- | --- |
| Critical | 認証なしで全データの読み書き・成り済ましができ、現構成で容易に悪用できる |
| High | 認可の全面的な迂回、CSRF 等で第三者が状態を破壊・大量投入できる、または本番化時に Critical 相当になる設計上の欠陥で現時点でも悪用経路がある |
| Medium | 限定条件下での情報漏えい(少数セルの復元等)、CPU/メモリの枯渇による可用性低下、共有環境での妨害 |
| Low | 多層防御の不足、軽微な情報露出、本番化時に必要となる設定の欠如 |
| Info | 現時点で悪用経路がない設計上の注意点、将来のリスク、コード品質に近い事項 |

| 確度 | 基準 |
| --- | --- |
| Confirmed | コードの到達経路と前提条件を確認し、既存の防御で止まらないことを検証した(概念実証を含む場合はその旨を記載) |
| Likely | 到達経路は確認したが、実行時条件(データ・環境)に依存する |
| Possible | コード上の疑いにとどまり、再現条件を確定できていない |
