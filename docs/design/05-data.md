# 05 データ設計

## 目的
アプリが扱うデータ(ダミーデータと追加データ)の構造と持ち方を定める。

## 含める内容
- データ一覧とエンティティ関係
- ダミーデータ(出所、生成方法、件数)
- 保存方法(ローカル)
- 個人を特定しない集計の定義

## 現時点で分かっていること

- テストデータの基本は競技提供データ。`sample-data/*.csv` から `app/src/data/seed.json` を生成する。 [事実、rule.md 3、AGENTS.md 1]
- sample-data にはユーザー情報が含まれる。設計書や資料には必要最小限しか転記しない。 [事実、AGENTS.md 5]
- 実在個人を識別できる情報は使わない。 [決定、rule.md 7]

| 参加申請(JoinRequest) | 申請ID、グループID、申請者(ダミーユーザーID)、ひとこと、**状態(申請中/承認/却下/取り下げ)**、申請日時、判断日時、判断者(幹事)、却下理由(持つかは未決、12章 #15)、**「最少人数でもOK」の同意フラグ(同意した日時を含む。同意しない人の扱いは未決、12章 #22)**、再エントリーの場合は再企画元の参加申請ID(案)。承認でメンバーに追加する | 4、13、18 |

| 通知(Notification。ローカルのダミー) | 通知ID、宛先(ダミーユーザーID)、種類、グループID、本文(定型文+人数などの値)、作成日時、既読。**種類: 最少人数到達、辞退期間の開始、辞退期間の終了(まもなく確定)、実行確定(実際の人数と参加者の概要つき)、中止、再企画の案内、辞退の受付(幹事向け)、条件変更(幹事が締切や最少人数を変えたとき)**。参加者の概要は個人が特定されない集計の値のみ | 18、4 |

### グループのデータに関する決定と案
- 人数上限は 2〜6人。1対1は人数2のグループとして扱い、データ構造をグループに一本化する。 [決定、オーナー]
- 幹事制: グループには作成者が幹事として1人いる。幹事が参加申請を承認・却下する。それ以外のメンバーは対等。前回の「管理者なし」を更新した。 [決定、オーナー]
- 幹事に与える権限の範囲(除名、プラン編集、設定変更)と、幹事の退会・不在時の引き継ぎ(次の幹事の決め方)は未決。役割は「幹事/メンバー」の2値で持ち、権限の範囲が決まるまで承認以外の特権を実装しない。 [未決、12章 #13・#14]
- 公開設定は公開/非公開の2種類。公開グループだけが一覧(柱3、17)に載る。非公開は招待コードを知る人だけが申請できる。 [決定(種類)、扱いの詳細は未決 12章 #17]
- 一覧に出す項目は、グループの公開項目(行き先、日程、タグ、空き人数、公式枠フラグ)と、メンバー概要(人数、年代帯の分布などの集計。個人を特定しない)。メンバー概要の粒度は 07 章・12章 #16。 [決定(4項目)/案(粒度)]
- メモ・チャット・費用メモの更新は、参加中メンバーの全員が行える(幹事に限らない)。 [案]
- 費用メモは金額をメモとして持つだけ。決済・送金のデータは持たない。 [案]
- チャット・通知はローカルのダミーデータで表し、外部サービスに依存しない。 [案、rule.md 3・6]
- 実行条件(柱18): 幹事が最少人数と締切を設定し、締切までに最少人数に達したら実行確定。状態(募集中、最少人数到達、辞退期間、実行確定、実施中、完了、中止)は Group が持ち、人数・締切・日付から決まる。状態遷移は 04 章。 [決定(実行条件)/案(状態名・持ち方)]
- 最少人数の範囲(案: 2〜人数上限、初期値 3、定員 2 のときは 2)。最少人数に幹事を含めるか(案: 含める)。 [未決、12章 #19]
- 参加申請に「最少人数でもOK」の同意フラグを持つ。辞退は専用の記録に残し、ペナルティ(不利益の情報)は持たない。 [決定(同意・辞退)/案(持ち方)]
- 中止したグループは削除せず状態「中止」で残し、再企画で作った新グループが元グループIDを参照する。前回の参加者への案内は、元グループの参加者(辞退者を含むか否かは未決)に通知を作って表す。 [案、12章 #23]
- 通知はローカルのダミーデータ。外部サービス(メール、プッシュ、LINE 等)は使わない。 [案、rule.md 3・6]
- 日時(締切など)の判定はダミー日付(デモ用の現在日付)で行い、実時間に依存しない案。 [案、12章 #26]
- 人数が 2 になる前の「1人で募集中」の扱い(人数1のグループを許すか)。 [未決、要確認]
