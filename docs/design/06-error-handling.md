# 06 エラー処理

## 目的
エラー時に原因と次の行動が分かる設計を定める(rule.md 9.1 ユーザビリティの観点)。

## 含める内容
- エラーの分類(入力、状態遷移、データ、通信相当、想定外)
- 画面ごとのエラー表示方針
- 同行の状態遷移に関するエラー(重複希望、承諾済みへの再操作、取り消し、辞退)
- ブロック・通報後の表示

## 現時点で分かっていること
- 原因と次の行動を表示する。 [決定、rule.md 9.1]
- 断りは、相手に傷つきにくい形で伝える。 [案、ideas.md G-9]
- 候補が見つからないときは、日程を広げる提案などを出す。 [案、G-14]
- 外部通信がないため、通信エラーはローカル保存・読み込みの失敗として扱う。 [推定]
- 詳細設計のエラー形式: API の応答は `{ error, reason?, message, fields?, detail? }` とし、`message` は利用者向けの日本語(原因と次の行動)を常に付ける。コードは 11 種(入力不正、権限なし、ブロック、存在しない、状態により不可、競合、回数超過など)で、HTTP ステータスはコードから一意に決まる。各モジュールの細かい理由は `reason` で表す。 [案、契約書 3.3]
- 存在を隠す扱い: 非公開グループの非メンバー、ブロック関係、招待コードの不一致は、すべて「存在しない」と同じ応答にする。 [案、契約書 5.5・7.2]
- 同時操作の競合: 版番号の照合で検出し、画面は最新を再取得して再入力を促す。競合ダイアログの差分表示などの作り込みは見送る。 [案、契約書 2.3・16.2]
- 通信失敗時: エラー表示部品で `message` を表示し、入力を保持する。段階的な再試行やオフライン表示は見送る。 [案、契約書 16.2]
- 各モジュールのエラー一覧(コード、発生条件、画面での表示)は docs/feature の各設計書にある。
