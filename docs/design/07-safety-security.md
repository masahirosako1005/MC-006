# 07 安全・セキュリティ・規制

## 目的
初対面の同行に伴うリスクと規制への対応方針、セキュリティ対策を定める。柱5〜8が中心。

## 含める内容
- グループ旅行の安全(13〜16)
- 安全機能: プロフィール公開範囲(5)、通報・ブロック(6)、本人確認・18歳確認(7)、禁止表現の制御(8)
- 安全の運用(迷惑行為への対応、合流の安全)
- セキュリティ対策(入力検証、XSS、秘密情報の扱い)
- 規制の整理と個人情報の扱い

## 現時点で分かっていること

### 安全機能
- 設計原則: 承諾がそろうまで連絡先・本名を見せない。公開情報は利用者が選ぶ。 [決定、旧 design.md 6]
- 柱5: プロフィール項目ごとの公開設定。 [案]
- 柱6: 通報・ブロックをいつでも使える。 [案]
- 柱7: 競技はログイン不要のため本人確認・18歳確認は**モック**。確認結果のみ保持。 [決定(モック)]
- 柱8: 恋愛・異性交際を連想させる文言・入力欄、性別での絞り込みは設けない。名称・訴求も同様。グループ参加を基本にする。グループ一覧の絞り込みにも同じ方針を適用する(性別は禁止、年齢は年代帯のみ。下の「論点」11)。 [案、ideas.md 5.5 の工夫案]
- 合流は日中・公共の場所を推奨。 [案、F-5]

### 規制(出会い系サイト規制法) [推定。法的判断ではない]
- 届出制。条件は「面識のない異性との交際を希望する人の情報を公衆が閲覧できる状態にし、連絡できるようにする」。 [事実(公開資料の理解)、ideas.md 7.5。警察庁解釈基準での裏取りは未実施]
- 同行フロー(プロフィール公開、選択、成立後の連絡)は該当性が最も高い設計に近い。 [推定]
- 18歳未満を巻き込まない設計が必要。旅行業法、個人情報も別途確認。 [要確認]

### セキュリティ
- 認証情報を含むファイル(`.env*` 等)をコード・資料に含めない。 [決定、rule.md 7、AGENTS.md 5]
- 入力検証、出力のエスケープ、ダミーデータのみ使用。具体策は未作成。

### グループ旅行の安全(柱13〜16)
方式は「公開グループを一覧から探して参加申請し、幹事が承認する」で決定済み。幹事は参加承認の役割を持つが、除名などの権限範囲は未決のため、安全は「承認という入口の確認」「退会のしやすさ」「通報・ブロック」を軸に設計する。見知らぬ人に見える情報が増える(一覧が公開される)点が、前回の招待制より安全面で重くなる。 [推定]

- 外部サービスは使わない。チャット・通知はローカルのダミーデータ/モックで表す。実在個人の情報は入れない。 [決定、rule.md 3・6・7]
- 承諾前は本名・連絡先を見せない原則は、グループへの参加申請にも適用する(参加が成立するまでメンバー一覧の詳細は見せない)。幹事の承認が「承諾」にあたる。 [案]
- グループ内でも、プロフィール項目は各利用者が選んだ公開範囲に従う(柱5)。グループの全員に全項目が見えるわけではない。 [案]
- 費用の分担メモ(柱16): 金銭の授受は扱わず、あくまで「メモ」とする。決済・送金・請求・外部決済サービスとの連携は対象外。画面に「記録のみ・送金はできない」と明記する。 [案]
- 柱8(禁止表現)は、グループ名、メモ、チャット、費用メモの項目名にも適用する。 [案]

#### 論点と選択肢(いずれも未決。オーナー判断)
1. 参加の承認。**決定済み: グループを作成した幹事が参加申請を承認する。** 前回の選択肢(招待コードのみ/全員承認/過半数/招待者+異議)は採らない。 [決定、オーナー、12章 #6]
   - 派生する論点は下の 7〜12 と 12章 #13〜#18。
2. メンバーの退会・除名。 [未決、12章 #7]
   - 案A: 退会のみ可(除名なし)。メリット: 揉め事が起きない。デメリット: 迷惑なメンバーを排除できない。
   - 案B: 幹事が除名できる。メリット: 判定が単純で排除できる。デメリット: 幹事の恣意で外される恐れ(下の 9)。幹事の権限範囲(7)と一体で決める。
   - 案C: 除名はせず、通報・ブロックで個別に避ける(下の3)。デメリット: グループには残る。
   - (前回の案「多数決で除名」は、幹事制になったため幹事案 B と比較する位置づけに変更。メリット: 幹事の独断を避けられる。デメリット: 判定が複雑。)
   - 共通の論点: 退会後のチャット履歴・費用メモ・スタンプ集計の扱い、人数が 2 を下回ったときにグループを解散するか。
3. 通報・ブロック(柱6)のグループ側の挙動。 [未決、12章 #8]
   - 案A: ブロックした相手のチャットの書き込みを自分の画面で非表示にするだけ(グループは変えない)。最小で軽い。
   - 案B: ブロックが成立したら同じグループに留まれない(どちらかが退会する)。安全だが、少人数のグループは崩れる。
   - 案C: 通報されたメンバーについて、他メンバーに通知しない(報復防止)。通報の運用は画面のみ(デモ)。
4. グループチャットの不適切な書き込み(柱8)。デモ範囲を最小にする案を含む。 [未決、12章 #9]
   - 案A(最小): 定型文のみ(「集合時間を変更したい」等)。自由入力なし。メリット: 禁止表現の制御が不要で安全。デメリット: 実用性が低い。
   - 案B: 自由入力+投稿の通報のみ(制御は事後)。メリット: 作りやすい。デメリット: 不適切な書き込みが先に出る。
   - 案C: 自由入力+入力時に禁止表現リストで弾く(柱8を適用)。メリット: 事前に抑止。デメリット: リスト作成と誤検知の対応が要る。
5. 未成年・本人確認(柱7)、公開範囲(柱5)のグループでの扱い。 [未決、12章 #10]
   - 本人確認・18歳確認は競技ではモック。グループ参加時にも確認済みを条件にするか(案: 参加条件にする。モックの確認結果を使う)。
   - 18歳未満を巻き込まない原則を、グループ(家族旅行など未成年が同席する場面)にどう適用するか。実運用では別論点。 [要確認]
   - 公開範囲: グループ内で見せる項目の初期値をどうするか(案: 参加が成立するまで最小限)。
6. 未決の維持: **未成年の扱い**は決めない。一覧は見知らぬ人に公開されるため、18歳未満が一覧・申請・幹事の立場に関わる場面は実運用で重い論点になる。デモではモックの18歳確認を使うか否かのみ。 [未決、12章 #10]
7. 幹事の権限の範囲。承認以外に、除名、プラン編集、設定変更(公開/非公開の切替、人数上限)、解散を持たせるか。 [未決、12章 #13]
   - 案A: 承認のみ(最小)。メリット: 幹事の影響が小さく、他メンバーは対等のまま。デメリット: 迷惑な参加者を外せない。
   - 案B: 承認+プラン編集・設定変更(除名なし)。メリット: 作成者の意図でプランを保てる。デメリット: 他メンバーの編集権(全員可の案)と衝突しうる。
   - 案C: 承認+除名+設定変更。メリット: 運営責任を幹事に集約でき、排除が可能。デメリット: 幹事の権限が強く、恣意的運用のリスク。
8. 幹事が退会・不在になったとき。 [未決、12章 #14]
   - 案A: 最も早く参加したメンバーに自動で引き継ぐ。メリット: 簡単で空白が生じない。デメリット: 本人の同意がない。
   - 案B: 現幹事が退会時に次の幹事を指名する。メリット: 意思が反映される。デメリット: 指名せず退会する場合の既定が要る。
   - 案C: メンバーの合意(または多数決)で選ぶ。メリット: 納得感がある。デメリット: 手間と判定ルールが要る。
   - 案D: 幹事不在でグループを解散(または募集停止)。メリット: 単純。デメリット: 旅行の途中でも終わる。
9. 幹事による恣意的な却下。申請者が不当に断られないか、幹事が属性で選別しないか。 [未決、12章 #15]
   - 案A: 却下理由を定型文から選ぶ(性別・年齢を理由にする選択肢は置かない)。メリット: 恣意と差別的運用を抑えやすい。デメリット: 選択肢の設計が要る。
   - 案B: 理由は任意で、却下は申請者に結果のみ通知する。メリット: 摩擦が少ない。デメリット: 不当な却下を検証できない。
   - 申請者は却下された結果と、通報の窓口(10)を使える。理由の具体的な表示方針は未決。
10. 申請者の通報・ブロック。幹事が申請者の公開プロフィールを見て、不適切だと判断したときの通報、および申請者が幹事・グループを通報できる導線(柱6)。通報は承認前からできるようにする案。ブロック済みの相手からの申請は幹事側に表示しない案。 [案、運用は画面のみ(デモ)]
11. 一覧に出す情報の粒度と禁止事項。[決定/案/未決は項目ごと]
    - **性別での絞り込みは禁止。一覧にも性別の表示・条件を設けない。** [決定、柱8 の維持]
    - **年齢を理由にした絞り込みは、恋愛を連想させない範囲に限る。** 絞り込みは「年代帯」(例: 20代、30代)の選択のみとし、年齢の細かい指定や「同年代のみ」「若い人」のような語は使わない。 [案、柱8 の運用方針]
    - メンバー情報の概要は、人数・年代帯の分布など、個人が特定されない集計にとどめる。人数が少ないグループ(例: 2〜3人)では年代帯の分布だけで個人が推測されうるため、表示の下限や丸め方を決める。 [案、要確認]
    - 公開範囲: 一覧に出す情報(プラン内容、空き、概要)と、詳細(参加前)に出す情報(幹事の表示名、プロフィールの一部)と、承認後にだけ見せる情報(メンバーの一覧、連絡手段)を段階で分ける。承認前に見せる範囲の具体は未決。 [案、12章 #16]
12. 公式枠(自治体のおすすめプラン)の信頼性表示。公式枠には「自治体公式」のバッジを付け、一般のユーザーが作るグループと区別する。なりすまし(一般ユーザーが公式を装う)を防ぐため、公式の表示は自治体担当者の操作でのみ付く設計とする。デモのダミーデータでは、公式表示は仮の主催者名で表す。公式でも安全が保証されるわけではない点を画面で誤解させない文言にする。 [案、12章 #18]
13. 非公開グループ(招待コード)。一覧に出さない一方で、コード流出の危険は残る。コードのみで参加できるのか、コード後も幹事の承認を要するのか。 [未決、12章 #17]
   - 案A: コード+幹事の承認(公開グループと同じ承認)。メリット: 流出に強い。デメリット: 招待した知人にも承認の手間。
   - 案B: コードのみで参加(承認なし)。メリット: 知人の参加が簡単。デメリット: 流出で見知らぬ人が入れる。幹事制の趣旨が弱まる。
14. デモの形との関係。グループ旅行は「同行成立中心」でも「集合型イベント中心」でも関わる。前者では成立後に 2人グループから拡張する形、後者ではイベント参加者がグループ化する形になる。どちらかは決めない。 [未決、01章]
