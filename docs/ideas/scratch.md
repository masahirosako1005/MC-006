# scratch：既存サイトの設計情報と、追加すべき機能

作成日: 2026-11-06
位置づけ: 設計書（[design.md](./design.md)）を起こすための下書き。

関連文書: [overview.md](./overview.md)（調査結果）、[ideas.md](./ideas.md)（構想とユーザーストーリー）

## 0. この文書の信頼度

- 既存サイトの情報は、**公開されているフロントエンド（HTML と JS バンドル）の静的解析**だけから起こしている。ログインはしておらず、バックエンドのコードや API の応答は見ていない。
- 各項目に、確度を付ける。
  - **［確認］**: コードや HTTP 応答で直接確認できたもの
  - **［推定］**: 文言や API 名から推測したもの
  - **［未確認］**: 見えていないもの

### 1.2 テナントの単位

- **キャンペーンが、テナントの単位。** URL は `/{campaign}/...`。`nttw-demo` はその 1 つ［確認］。
- 認証の API が `auth.raund.net/{campaign}/...` とキャンペーン単位。ブラウザに保存する識別子も、キャンペーン名付き（`{campaign}-user-device-uuid`、`{campaign}-username`）［確認］。
- そのため、**利用者はキャンペーンごとに別アカウント**になっている可能性が高い［推定］。
- ルートの 1 つに `deploy-system-root` というキャンペーン名がある。役割は不明［確認（存在）／未確認（役割）］。

| 項目 | 内容 | 確度 |

### 1.6 キャンペーンごとの設定

JS に含まれる API スキーマの説明文から、機能のオン・オフや見た目を、キャンペーン単位で設定できることが分かる［確認（文言）］。

- 機能フラグ: EC、復元、多言語、テストモード、LINE 友だち追加、GPS 照合など
- 見た目: メインカラー、スタンプの形状、トップ画像、マップピンなど
- 期間: 開催・表示・押印可能期間、期間前後のメッセージ
- 地図: 中心座標、画像マップ

→ **新機能も、キャンペーンごとのフラグで有効にする作りが、既存の方式に合う**［推定］。

## 2. 必要になりそうな機能と、既存からの差分

凡例: **流用**＝そのまま使える、**拡張**＝既存の機能に手を入れる、**新規**＝既存にない。

### 2.1 旅行者向け

| 機能 | 関連ストーリー | 既存で使えるもの | 追加すべきこと | 区分 |
|---|---|---|---|---|
| 全国のキャンペーン一覧（ランディングページ） | G-1 | キャンペーン単位の `/{campaign}` | キャンペーンを横断する一覧ページ。地方・テーマ・季節での探索 | 新規 |
| 旅先の探索、保存 | H-1、H-3 | スポット一覧、「行きたい」登録 | キャンペーン単位の保存（旅先の保存）。テーマ・季節の分類 | 拡張 |
| 旅行日程・人数・グループの入力 | G-3〜G-5 | なし | 旅程（行き先、日程、日程の幅、人数）の入力と保存 | 新規 |
| 参加予定人数の表示 | H-2 | なし | 同じ地方・日程の参加予定の集計と表示 | 新規 |
| 同行候補の表示 | G-6 | なし | 条件が合う人・グループの抽出と一覧 | 新規 |
| プロフィールの作成と公開範囲の制御 | G-7 | 利用者情報、ハンドルネーム | 利用者のプロフィール（写真、年代、一言、旅の目的）。項目ごとの公開設定 | 新規 |
| 同行の希望、承諾、断り | G-8、G-9 | なし | 希望の送信、受信側の承諾・断り、双方成立の管理 | 新規 |
| 成立後の連絡（チャット） | G-10、G-11 | なし | 双方が承諾したときだけ使えるメッセージ機能 | 新規 |
| 日程変更・辞退 | G-13 | なし | 成立後のキャンセルと相手への通知 | 新規 |
| 候補がいないときの通知 | G-14 | 通知、LINE 連携 | 候補の出現、日程を広げる提案の通知 | 拡張 |
| 同行しながらラリーを回る | G-11、G-12 | スタンプ・ポイント獲得、スポット、地図 | 同行者どうしでのスタンプの共有表示（任意） | 拡張 |
| 合流の確認 | F-5 | ジオフェンス、GPS 照合 | 待ち合わせ場所への到着確認（任意） | 拡張 |
| 記録と振り返り | C-2 | 写真投稿、活動履歴、履歴画面 | 同行者・旅の記録のまとめ | 拡張 |
| 再訪の動機（回数に応じた特典・称号） | C-4 | ポイント、特典、リセット（周回） | 回数の通算、称号 | 拡張 |
| 複数都市の横断（共通アカウント、旅の記録） | D-1、D-2 | なし（キャンペーンごとに分かれている［推定］） | キャンペーンをまたぐ利用者の識別 | 新規 |
| 少人数の集合型イベント | A-6 | アンケート、特典（応募フォーム） | イベントの日程・定員・申込管理 | 新規 |

### 2.2 地元の人（協力者）向け

| 機能 | 関連ストーリー | 既存で使えるもの | 追加すべきこと | 区分 |
|---|---|---|---|---|
| 協力者の登録と管理 | B-3、E-2 | なし | 協力者の登録、承認、プロフィール | 新規 |
| 同行できる枠の登録 | B-2、B-3、G-16 | なし | 日時、回数、内容、定員の設定 | 新規 |
| 紹介スポットの登録 | B-1、B-4 | スポット管理［未確認］ | 協力者によるスポット・おすすめの登録 | 拡張 |
| 申込の断り | B-5 | なし | 承諾・断りと、ブロック | 新規 |

### 2.3 自治体・運営者向け

| 機能 | 関連ストーリー | 既存で使えるもの | 追加すべきこと | 区分 |
|---|---|---|---|---|
| 出会い軸のキャンペーンのテンプレート | E-1 | キャンペーンの設定（フラグなど） | 同行機能のオン・オフと、テンプレート | 拡張 |
| 指標の確認（参加、リピート、成立） | E-3 | 計測タグ、`/api/v1/tracking` | 個人を特定しない集計画面。成立率などの指標 | 新規 |
| 参加者の声の収集 | E-4 | アンケート | 同行後のアンケート | 流用 |
| 送客リンクの作成 | H-6 | なし | 地方・日程の条件を載せたリンクの発行 | 新規 |
| 流入元別の計測 | H-5 | 計測タグ | 流入元から、登録・成立までの紐付け | 拡張 |
| 本人確認 | F-1 | なし | 身元・年齢の確認の手段（外部サービスの利用を含む） | 新規 |
| 通報・ブロック・利用制限 | F-2、F-3 | なし | 通報の受付、確認、対応の運用画面 | 新規 |
| 同意の管理（連絡先、データの提供） | F-4、E-5 | なし | 同意の取得と履歴 | 新規 |

### 2.4 規模感

「新規」が多く、**既存の機能の延長ではなく、新しい領域（利用者どうしの関係）を作る**ことになる。既存で使えるのは、ラリー、スポット、特典、通知、LINE、計測といった周辺である。

## 3. 追加が必要になるデータ（案）

既存にない、新しい概念。名称と項目は仮。

| データ | 内容 |
|---|---|
| 旅程（Trip） | 利用者、行き先（キャンペーン）、日程、日程の幅、人数 |
| グループ（Party） | 代表者、メンバー、人数 |
| プロフィール（Profile） | 表示名、写真、年代、一言、旅の目的、項目ごとの公開設定 |
| 同行の希望（CompanionRequest） | 送信側・受信側の旅程、状態（送信、承諾、断り、取り消し） |
| 同行の成立（CompanionMatch） | 双方の旅程、成立日時、状態 |
| メッセージ（Thread、Message） | 成立した同行の会話 |
| 協力者（Host）、同行枠（HostSlot） | 地元の人の登録、日時、定員 |
| 本人確認（Verification） | 確認の種類と状態（確認結果のみを持つ） |
| 通報・ブロック（Report、Block） | 通報の内容、対応状況、ブロックの関係 |
| 評価（Rating） | 同行後の評価 |
| 同意（Consent） | 連絡先の共有、データの提供の同意と履歴 |
| 共通アカウント（Identity） | キャンペーンをまたぐ利用者の識別（既存の利用者と紐付け） |

## 4. 設計上の論点

| 論点 | 内容 |
|---|---|
| 利用者の識別 | 既存はキャンペーンごとに分かれている［推定］。複数都市の横断と、相乗りマッチングの前提になるため、**共通の識別をどう持つか**が最大の技術的論点 |
| 新しい通信先 | CSP の `connect-src` は既存のドメインに限られる。チャット、本人確認などの外部サービスを使う場合、**CSP の変更が必要** |
| 既存のバックエンドとの関係 | 既存の API に機能を足すのか、別のサービスとして作って連携するのか。バックエンドの実装が見えていないため、判断できない |
| 個人情報とプライバシー | プロフィールの公開範囲、連絡先の扱い、位置情報（GPS）の扱い、保存期間 |
| 規制 | プロフィール公開、相手の選択、連絡がそろう設計は該当性が高い（[ideas.md 7.5](./ideas.md)）。設計の前に確認 |
| 安全 | 本人確認、18 歳未満の排除、通報・ブロック、迷惑行為への対応、合流の安全 |
| 通知 | 同行の希望・承諾・メッセージの通知。LINE 連携が使える（友だち追加が前提） |
| 多言語 | 既存は 3 言語。プロフィールやメッセージの翻訳をどうするか |
| 運用 | 通報の確認、本人確認の審査、協力者の承認を、誰がどう運用するか |
| 計測 | 流入元から、登録・成立までの紐付け。個人を特定しない集計 |

## 5. 確認が必要なこと（ログイン後・ソース・依頼元）

1. 既存サービスにログインし、画面とデータの持ち方を確認する（テスト用アカウントが必要）。
2. 利用者がキャンペーンごとに分かれているかを、実際に確認する。
3. 既存の API 仕様書、リポジトリ、管理画面の有無を、依頼元に確認する。
4. 既存のバックエンドの構成（実装、DB、基盤）を確認する。
5. 現在の顧客、契約形態、価格帯を、依頼元に確認する（収益構造の前提）。
6. 全国横断のランディングページが既にあるかを確認する（`deploy-system-root` の役割を含む）。
7. 本人確認、チャット、通知などに、使える外部サービスの方針があるかを確認する。
