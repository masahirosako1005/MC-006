# 設計書ドラフト：反映すべき事項

作成日: 2026-11-06
ステータス: 設計書に反映すべき事項の整理。**設計の確定ではない。**

関連文書: [overview.md](./overview.md)（既存サイトの調査）、[ideas.md](./ideas.md)（構想・ユーザーストーリー・法規制・収益）、[scratch.md](./scratch.md)（既存の設計情報と差分）

## 0. この文書の使い方

- 設計書を書くときに、**何を前提にし、何を決めてから書くか**を整理した文書。
- 各項目に、状態を付ける。
  - **［決定］**: 議論で合意した方針
  - **［案］**: 議論で出た案。確定していない
  - **［未決］**: 設計の前に決めるべきこと
  - **［要確認］**: 事実の確認が必要なこと

## 1. 目的とスコープ

### 1.1 目的［決定］
- 既存の観光キャンペーン・観光ラリーのサービスを、**利用者にも自治体にも価値のあるサービス**に発展させる。
- 利用者には、旅をきっかけに、**どこかの誰かと出会う**体験を提供する。
- 自治体には、魅力的なキャンペーンを組むことで、**出会いの場として「選ばれる」動機**を提供する。

### 1.2 設計の前提［決定］
- 利用者の主目的は、**出会い・つながり**。観光（ラリー）は、そのきっかけを作る手段。
- 移住は、利用者が望む場合の**付加的な要素**。前面に出さない。
- リピートの意思は自治体のもの。サービスは、選ばれる動機を作る側。
- 自治体どうしの競争は、肯定的に捉える。
- 主な顧客は**自治体**。地元事業者の協賛・手数料を副の収益にする［案、ideas.md 7.6］。

### 1.3 対象外（今回の設計に含めない）［案］
- 利用者課金による出会い機能（規制の該当リスクが上がるため）
- 恋愛・結婚を主目的にした機能（規制の確認が終わるまで）
- 宿泊・交通の販売（旅行業法の確認が必要なため）

## 2. 設計の前に決めること（ブロッカー）

設計書を書く前に、答えを出す必要がある事項。

| # | 決めること | 影響する設計 | 状態 |
|---|---|---|---|
| 1 | **規制への対応方針**: 相乗りマッチング（プロフィール公開、相手の選択、連絡）を、どこまで作るか。警察署または弁護士への確認結果 | 機能の範囲、画面、文言、名称 | 未決・要確認 |
| 2 | **出会いの形**: 緩い交流、一緒に回る、集合型イベント、1 対 1 のどこから始めるか | MVP の範囲 | 未決 |
| 3 | **利用者の識別**: キャンペーンをまたぐ共通の識別を持つか | データ設計、認証、複数都市の機能 | 未決・要確認 |
| 4 | **既存システムとの関係**: 既存の API に足すか、別サービスにするか | アーキテクチャ全体 | 要確認 |
| 5 | **地元側の担い手**: 誰が、どんな動機で参加するか | 協力者機能、運用 | 未決 |
| 6 | **安全の水準**: 本人確認の方法と水準 | 認証、運用、費用 | 未決 |
| 7 | **成果の指標**: 自治体に説明する指標 | 計測、集計画面 | 未決 |
| 8 | **ターゲットの入口**: 旅行サイト経由とアプリ内探索のどちらを主にするか | 集客導線、ランディングページ | 未決 |

## 3. 機能の範囲

### 3.1 機能の優先度（案）

優先度は、[ideas.md](./ideas.md) のユーザーストーリーに対応させる。

| 段階 | 目的 | 含める機能（案） | 主なストーリー |
|---|---|---|---|
| **第 1 段階** | 規制リスクが低い形で、出会いの価値を確かめる | 全国のキャンペーン一覧、旅先の探索・保存、地元の人の紹介・おすすめ、集合型イベント、同行後の連絡（双方の希望がある場合）、記録・振り返り、通報・ブロック、本人確認（最低限）、指標の集計 | G-1、G-2、H-1、H-3、H-4、B-1、A-6、C-1、C-2、F-2、E-3 |
| **第 2 段階** | 同行の仕組みを加える（規制の確認後） | 旅程の入力、参加予定の人数表示、同行候補の表示、希望・承諾、成立後のチャット、協力者の同行枠 | G-3〜G-16、H-2、B-2、B-3 |
| **第 3 段階** | 関係の継続と、都市の横断 | 回数に応じた特典・称号、複数都市の横断、自治体向けの情報提供 | C-3〜C-5、D-1〜D-3、E-5 |

> 理由: 規制の該当性が最も高いのは、プロフィール公開・相手の選択・成立後の連絡がそろう設計（ideas.md 7.5）。第 1 段階では、これを避ける形で価値を検証する。**この段階分けは案**であり、1 の結論で変わる。

### 3.2 利用者の流れ［決定（流れ）／案（詳細）］

```
全国のキャンペーンがあるランディングページ
  ├─ アプリ内で旅先を探す（入口 A）
  └─ 外部（旅行サイトなど）から、地方・日程を引き継いで来る（入口 B）
        ↓
行きたい地方を選ぶ → 旅行日程を入れる → 参加者・グループを入れる
        ↓
同日程で旅をしている人・グループの候補を見る
        ↓
相乗りの希望を出す → 相手が、希望側のプロフィールを見て承諾 → 成立
        ↓
相乗りでラリーを回る → 記録・振り返り → 再訪のきっかけ
```

詳細は [ideas.md 5.5、5.6](./ideas.md)。

## 5. リスク（設計書に書くこと）

| リスク | 内容 | 対策の方向（案） |
|---|---|---|
| 規制の該当 | 相乗りマッチングが、インターネット異性紹介事業に当たる | 目的を「旅の同行者探し」に限定、性別での絞り込みをしない、警察署・弁護士に確認。段階的に導入 |
| 安全 | 初対面の同行での事故・迷惑行為 | 本人確認、18 歳未満の排除、通報・ブロック、公共の場所での合流の推奨 |
| 成立しない（コールドスタート） | 同じ地方・日程の人が集まらない | 日程の幅、地元の人の枠、集合型イベント、集客を地域と時期に集中 |
| 地元側の供給不足 | 協力者が集まらない | 自治体の事業と連携、負担を自分で決められる設計 |
| 識別の分断 | キャンペーンごとに利用者が分かれ、横断ができない | 共通の識別の導入（既存の利用者との紐付け） |
| 既存システムへの影響 | 既存のバックエンドの制約で、機能を足せない | 別サービスとして作り、連携する案も検討 |
| 自治体の予算・成果 | 単年度、成果指標の説明が必要 | 説明できる指標の設計、事業者の協賛の併用 |
| 位置づけの誤解 | 恋愛目的と受け取られる | 名称・訴求・文言を、同行者探しに統一 |

## 6. 設計の原則（案）

設計書の全体に通す方針。議論の内容から起こした。

1. **目的は「出会い・つながり」。ただし、サービスの位置づけは「旅の同行者探し」にそろえる**（規制と誤解の回避）。
2. **相互の同意がそろうまで、連絡先と本名を見せない。**
3. **公開する情報は、利用者が選ぶ。**
4. **既存のキャンペーン単位の仕組み（フラグ、期間、見た目）に沿って、機能を有効にする。**
5. **個人を特定しない集計を、自治体に提供する。**
6. **小さく始め、段階的に広げる。**
