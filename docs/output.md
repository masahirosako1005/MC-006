## 1. 3 つの成果物の関係

```
ideas.md（構想・ストーリー）
   │
   ├──→ ① 提案書（なぜやるか、何をやるか、どう価値が出るか）
   │        └ スライド化するプロンプトとして提出
   │
   ├──→ ② 設計書（どう作るか）  ←── scratch.md（既存の設計情報）、design.md（反映事項）
   │
   └──→ ③ 開発成果物（動くもの。設計書の一部を実装）
            └ 提案書のデモ、設計書の裏付けに使う
```

- 提案書は「**何を、なぜ**」、設計書は「**どう作るか**」、開発成果物は「**動くことの証明**」を担う。
- 3 つの内容がずれないように、**同じ用語、同じユーザーストーリー、同じ画面**を使う。

## 2. 成果物 1：提案書（スライド化するためのプロンプト）

### 2.1 何を提出するか
- スライド作成のツールや AI に貼って、そのままスライドを生成できる**プロンプト**（Markdown のテキスト）。
- スライドそのものではなく、**スライドの構成と中身を指示する文章**が成果物。
- 置き場所の案: `docs/proposal-prompt.md`。

### 2.2 プロンプトに含めるもの（案）

| 要素 | 内容 |
|---|---|
| 目的と聞き手 | 誰に、何を判断してもらうための提案か（依頼元・自治体など。**要確認**） |
| トーン・形式 | 枚数、1 枚あたりの情報量、図の使い方、色や雰囲気 |
| スライドごとの指示 | タイトル、載せる文、図表の内容、強調したい 1 点 |
| 数字・事実の扱い | 根拠のある事実と、仮説を区別して書く指示 |
| 禁止事項 | 未確認のことを断定しない、恋愛を前面に出さない |

### 2.3 スライド構成（案）

| # | スライド | 主な内容 | 素材 |
|---|---|---|---|
| 1 | タイトル | 提案名、一言の価値 | — |
| 2 | 社会課題 | 都市集中、地方の過疎化、人とのつながりの減少 | ideas.md 1 |
| 3 | 観光ラリーの課題 | 体験が完結する、再訪の理由が弱い、帰ると思い出されない | ideas.md 1、会話の整理 |
| 4 | 発想の転換 | 観光が主目的から、出会い・つながりが主目的へ | ideas.md 2 |
| 5 | 提案するサービス | 一言の説明、利用者・自治体への価値 | ideas.md 3 |
| 6 | 誰の、どんな困りごとか | ペルソナ（旅行者、地元の人、自治体） | ideas.md 4 |
| 7 | 利用の流れ | ランディングページ→行き先→日程→候補→相乗り→旅 | ideas.md 5.5 |
| 8 | 再訪を生む仕組み | 人との結びつき、積み上がり、期待が育つ | ideas.md 2 |
| 9 | 入口と集客 | 探索と外部流入、自治体の導線 | ideas.md 5.6 |

| 12 | 収益と自治体への価値 | 自治体を主軸に、事業者の協賛を併用 | ideas.md 7.6 |
| 13 | デモ | 開発成果物の画面（③） | 成果物 3 |

### 2.4 完成の基準（案）
- そのまま貼って、ほぼ手直しなしでスライドが作れる。
- 事実と仮説が、はっきり区別されている。
- 開発成果物のデモと、話が合っている。

## 3. 成果物 2：設計書

### 3.1 何を提出するか
- 新機能の**設計をまとめたドキュメント**。
- 置き場所の案: `docs/design-spec.md`（反映事項をまとめた `design.md` とは別に、本体を作る）。

### 3.2 含めるもの
章立ては、[design.md 4 章](./ideas/design.md)の案に従う。

| 章 | 書くこと |
|---|---|
| 目的・背景、スコープ | 何のために、どこまで作るか（段階分けを含む） |
| 要件 | ユーザーストーリー、受け入れ条件 |
| 画面・フロー | 画面一覧、遷移図、入口 A・B |
| システム構成 | 既存との関係、追加するコンポーネント |
| データ設計 | 既存データ、追加データ（旅程、プロフィール、同行の成立など） |
| API 設計 | 追加するエンドポイント |
| 認証・本人確認、安全・運用 | 識別、本人確認、通報・ブロック |
| 法規制・プライバシー | 規制の整理、個人情報の扱い |
| 計測・指標、収益 | 自治体に説明する指標、収益構造 |
| 非機能要件、リスク、マイルストーン | 多言語、CSP、段階的な計画 |

### 3.3 完成の基準（案）
- **設計の前に決めること**（design.md 2 章）が、決定済みか、決まっていない理由と暫定の方針が書いてある。
- 既存サイトの情報は、**確認済みのことと推定を区別**して書いてある。
- 開発成果物の実装が、この設計書のどの部分に当たるか分かる。

### 3.4 注意
- 既存のバックエンドや API の仕様は、見えていない。設計書では、**推定に基づく部分を明示**し、確認後に直せる形にする。

## 4. 成果物 3：ローカル環境での開発成果物（一部はモック可）

### 4.1 何を作るか（案）
設計書の一部を、**ローカルで動かせるアプリ**として実装する。全部を作る必要はなく、**提案書のデモで見せる流れが動くこと**を優先する。

### 4.2 実装の方針（案）

| 項目 | 方針 | 理由 |
|---|---|---|
| 技術 | 既存に合わせて、Next.js、Mantine、Zustand | 既存のサービスに取り込む想定にできる（既存の構成は scratch.md 1.1） |
| データ | **モック**（ローカルの JSON、またはモックの API）を使う | 本番の API や利用者には触れない。バックエンドの仕様も見えていない |
| 外部サービス | 本人確認、チャット、LINE などは**モック** | 認証情報や費用が不要。デモの再現性が高い |
| 動かし方 | ローカルでの起動手順を README に書く | 提出先が、そのまま動かせる |

> **既存の本番サイトの API や、実際の利用者のデータは、開発に使わない。** 開発用に、別のデータを用意する。

### 4.3 実装する範囲（案）

デモの流れに沿って、次の順で作る。優先度が高いものから実装し、時間が足りなければ後ろを削る。

| 優先 | 機能 | 内容 | 実装の度合い |
|---|---|---|---|
| 1 | 全国のキャンペーン一覧（ランディングページ） | 地方・テーマで探す、旅先の保存 | 画面 + モックデータ |
| 2 | 旅程の入力 | 行き先、日程（幅）、人数・グループ | 画面 + 保存（ローカル） |
| 3 | 同行候補の一覧 | 同じ地方・日程の人・グループ、プロフィール（公開項目を選べる） | 画面 + モックデータ |
| 4 | 相乗りの希望・承諾 | 希望を出す、受け側で承諾・断り、双方成立 | 画面 + 状態遷移（ローカル） |
| 5 | 成立後の連絡 | 双方成立後にだけ使えるメッセージ | モック（簡易） |
| 6 | 入口 B（外部から来る） | 地方・日程を引き継いで着地 | URL パラメータで再現 |
| 7 | 安全の機能 | 通報・ブロック、公開範囲の設定 | 画面 + モック |
| 8 | 自治体向けの指標画面 | 参加、成立、再訪の集計（個人を特定しない） | 画面 + モックデータ |
| 9 | 地元の人の枠 | 同行できる枠の登録、旅行者の申込 | 画面 + モックデータ |

- 規制を考慮し、画面の文言、名称は**「旅の同行者探し」**にそろえる。恋愛や異性交際を連想させる文言、入力欄、性別での絞り込みは設けない（[ideas.md 5.5](./ideas/ideas.md)）。
- デモで見せる 1〜4 を、最初に動くようにする。

### 4.4 デモのシナリオ（案）
1. 旅行者（ミサキ）が、全国のキャンペーン一覧から、行きたい地方を選ぶ。
2. 旅行日程と人数を入れる。
3. 同じ日程の人が見つかり、プロフィールを見て、相乗りの希望を出す。
4. 相手が承諾し、成立する。連絡が使えるようになる。
5. 当日のラリーを一緒に回る（スタンプの画面）。
6. 自治体の担当者（タナカ）が、成立数や再訪を指標画面で見る。

### 4.5 完成の基準（案）
- README の手順で、ローカルに起動できる。
- デモのシナリオ（4.4）が、最初から最後まで通る。
- モックの部分が、画面上や README で**モックだと分かる**。
- 設計書のどの部分の実装かが、対応づけてある。

## 5. 成果物ごとの作業と依存

| 成果物 | 先に必要なこと | 依存 |
|---|---|---|
| 提案書 | 構想の整理（済）、デモの画面 | 開発成果物のデモ画面を、13 枚目に使う |
| 設計書 | design.md の「決めること」の結論（または暫定の方針） | 規制の確認結果、既存システムの確認 |
| 開発成果物 | 画面とデータの設計（設計書の画面・データの章） | 設計書の第 1 段階、第 2 段階の範囲 |

**進める順序の案**
1. 「決めること」に、暫定の方針を置く（規制は、安全側の設計を暫定とする）。
2. 設計書の、要件、画面・フロー、データ設計を書く。
3. 画面とデータに沿って、開発成果物（優先 1〜4）を作る。
4. 開発成果物の画面を使って、提案書のプロンプトを作る。
5. 設計書の残りの章と、開発成果物の残り（優先 5〜9）を仕上げる。

## 6. 成果物が満たすべき共通の要件（案）

- **事実と推定を区別する。** 既存サイトの情報は、ログイン前の調査に基づく。確認していないことを断定しない。
- **用語をそろえる。** サービスの位置づけは「旅の同行者探し」。キャンペーン、旅程、同行の希望、成立などの用語を、3 つの成果物で統一する。
- **規制と安全への配慮を、明示する。** 提案書、設計書、実装のいずれにも、規制の整理と安全の機能を載せる。
- **自治体への価値を示す。** 利用者の体験だけでなく、自治体の成果（指標）を示す。

## 7. 成果物ごとの想定されるリスク

| リスク | 内容 | 対策の方向 |
|---|---|---|
| 範囲が広すぎる | 9 つの機能すべてを作る時間がない | 優先 1〜4 に絞って先に完成させる |
| デモが動かない | モックの不具合、環境依存 | 起動手順を README に書き、別の環境で動作を確認する |
| 設計と実装がずれる | 設計書と、作った画面・データが合わない | 設計書の画面・データの章を先に書く |
| 規制の指摘 | 同行マッチングの設計が、規制の観点で問題と見なされる | 文言・設計を安全側にそろえ、確認が済んでいないことを明記する |
| 推定の誤り | 既存サイトの情報が実際と違う | 推定と明記し、確認後に修正する |

## 8. 提出物の置き場所（案）

```
  design.md            設計書に反映すべき事項

```

## 9. 作成前に確認したいこと

1. **提出先と聞き手**: 誰が、何を基準に評価するか。
2. **提出の形式**: プロンプトの形式（Markdown、文字数の制限、使うスライドのツール）、設計書の形式（Markdown、Word、PDF など）。
3. **開発成果物の条件**: 使ってよい技術、動かす環境、モックでよい範囲の考え方、提出の方法（リポジトリ、ZIP、デモ動画など）。
4. **期限**。
5. **既存サービスの扱い**: 既存のコードやデータを、開発の素材として使ってよいか。
6. **本番に近いデモの要否**: モックのみでよいか、実際の API とつなぐ必要があるか。

## 10. 前提（想定）

- 提案書は、依頼元（ミッションを出した側）に向けて、構想の価値と進め方を示すもの。
- 設計書は、実装する人が読んで、迷わず進められる水準。
- 開発成果物は、提案を「見て分かる」ものにするための実装で、本番の品質は求めない。

## 11. 想定がずれていた場合

- 提案書の聞き手が自治体なら、2.3 の構成の重みを、自治体への価値（9、12 枚目）に寄せる。
- 設計書が、実装のためではなく、検討の資料なら、章を減らし、論点と選択肢を厚くする。
- 開発成果物に、本番の API との接続が必要なら、4.2 の「データはモック」の方針を見直し、認証や接続の確認を先に行う。
