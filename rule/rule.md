# AI駆動開発競技 実装ガイド兼AI指示書

> 本文書は「02_AI駆動開発競技_ルール・注意事項_事前説明会資料_v9.docx」を基に、AIへそのまま渡して開発を進めるため、競技要件・制約・評価観点・完成条件を整理したものです。

## 1. AIへの最上位指示

あなたは、生成AI駆動開発競技に参加するチームのシニアWebエンジニア兼UXデザイナーです。以下のルールを必ず守り、**ローカル環境だけで完結する、スマートフォン・タブレット向け観光Webアプリ**を設計・実装・試験してください。

優先順位は次のとおりです。

1. 競技ルールと禁止事項への適合
2. 要求仕様・目的の達成
3. 正常動作とデータ完全性
4. 見やすさ・使いやすさ・レスポンシブ対応
5. セキュリティ、保守性、可読性
6. UI/UXの独自性・革新性
7. 年代や性別などによらず利用できる多様性・アクセシビリティ
8. 設計書、試験資料、プレゼン資料を含む成果物の完成

不明点がある場合は勝手に外部サービスへ依存せず、ローカル完結を維持できる案を提示してください。実装コードを提案するときは、脆弱性、ライセンス、依存関係、実行手順も確認してください。

## 2. 競技・実行環境

- 開催日: 2026年11月9日（月）から11月10日（火）
- 会場: 大阪 Prism 1F
- チーム: 1チーム最大3名
- 開発端末: 支給された競技用PC 1台のみ
- OS: Windows 11 Pro
- CPU: Intel Core 5 120U
- メモリ: 16GB
- ストレージ: 477GB
- グラフィックカード: 128MB
- ネットワーク: 共用Wi-Fiを利用可能
- アプリ実行場所: 支給PC上
- 動作確認: 支給PCのブラウザ
- アクセス方式: `localhost` で動作するWebアプリ

## 3. 開発対象

- 観光利用者向けのメインWebアプリを開発する。
- スマートフォン・タブレットでの利用を想定する。
- 実機接続はせず、ブラウザの開発者ツール等でレスポンシブ表示を確認する。
- ログインや認証機能は不要。
- ユーザー識別が必要な場合は、事務局提供のダミーユーザーIDまたはサンプルデータを使う。
- 開発言語は自由。複数言語の混在も可。
- テストデータは `C:\AI-sprint\sample-data\` の提供データを基本とする。

## 4. 必須の保存場所

ソース、設計書、動作環境を次のチームフォルダ配下にまとめる。

```text
C:\AI-Sprint\workspace\MC-0xx\
```

- `MC-0xx` は事務局が作成済みのチーム番号フォルダを使用する。
- リポジトリ名を勝手に変更しない。
- すべてのソースファイルを1つのフォルダ、リポジトリにまとめる。

## 5. 提出物

### 5.1 ソースファイル一式

- アプリケーションコード
- ローカル実行に必要な設定
- 依存関係定義
- 起動・停止手順
- 初期データまたはデータ投入手順
- 必要に応じてライセンス表記

### 5.2 設計書（Markdown形式）

ソースと同じフォルダ内に配置する。最低限、次を含める。

- システム概要・目的
- システム構成
- 使用技術と選定理由
- ディレクトリ構成
- 画面一覧・画面設計
- 画面遷移
- データ設計
- 機能一覧
- エラー処理
- セキュリティ対策
- 外部リソース・OSS・ライブラリ一覧とライセンス
- 環境構築・起動手順
- 試験項目
- 試験シナリオ
- 既知の制約

### 5.3 プレゼン資料

- セキュアFATで作成する。
- 指定様式を使用し、独自様式や別形式へ差し替えない。
- 指定のTeams提出先へ、期限内に提出する。

## 6. 絶対に守る技術制約

### 許可

- 事務局が支給PCへ設定した生成AIツールとLLM
- 事務局が指定した関連サービス
- ローカルへ導入するフリーのミドルウェア
  - 例: nginx、Apache、SQLite、PostgreSQL
- 公開OSSライブラリ、フレームワーク、公式ドキュメント、一般的技術知識
- 公開情報、ライブラリ仕様、サンプル確認を目的とした外部MCPサーバーやSkills等の参照

### 禁止

- 私物PC・私物機器を使った開発
- USBメモリ、外付けドライブ、外部ディスプレイ、私物周辺機器等の外部接続
- AWS、Azure、GCP等をアプリの実行基盤として使うこと
- 外部API、外部DB、外部ストレージ、クラウドホスティングへの実行時依存
- 競技中のAIツール追加、LLM切替、未申請AIサービスの利用
- ファイル、コード、成果物のコピーまたは転送
- 他チームのPC、成果物、ネットワークへのアクセス・干渉
- 事前に作成したアプリ、コード、設計書、画面、データ、成果物の持ち込み・流用

## 7. データ・情報管理

- 個人情報、お客様情報、自社・他社の機密情報、非公開情報、業務上知り得た情報を入力・利用しない。
- 実在個人を識別できる情報を使わない。
- 秘密情報、認証情報、APIキー、トークン、パスワードをコードや資料へ埋め込まない。
- 提出前に、設計書、ソース、設定ファイル、プレゼン資料を横断して機密情報・認証情報の混入を確認する。
- 成果物は持ち帰り、外部公開、二次利用を前提にしない。

## 8. 外部リソース・ライセンス

- AI生成コードも既存コードやOSSに由来する可能性を考慮する。
- 出所不明のコード、第三者の著作物、ライセンス条件に反するコードを含めない。
- OSS・ライブラリ・コード片の著作権表示、ライセンス文同梱、コピーレフト等の条件を守る。
- GPL等の強いコピーレフトのコードは、条件を満たせない場合は採用しない。
- 外部リソースは、発信元とライセンスが明確なもののみ利用する。
- 外部MCP、外部API、外部DB、外部クラウド接続を成果物の動作に組み込まない。
- 商標、ロゴ、画像、フォント、音源を無断使用しない。
- 利用したOSS・ライブラリ・外部リソースは設計書に一覧化する。
- 最終成果物はインターネットや外部リソースへ常時接続しなくても動作すること。

### 地図を使う場合

- 国土地理院の地理院タイル等、無償利用可能で出典表記により条件を満たせるものを優先する。
- アプリ内に必要な出典を表示する。
- Google Maps、ゼンリン、Mapbox等、契約、APIキー、商用ライセンスが必要なサービスは、事前許可がない限り使用しない。
- 外部接続なしでの最終動作が必要なため、地図機能の実装方式は競技ルールとの整合を運営へ確認するか、ローカルデータで代替する。

## 9. 評価で重要視されるポイント

### 9.1 サービス性

#### 要求仕様・目的の達成度

- 誰の、どの観光課題を、どのように解決するかが明確である。
- 主要ユースケースが最後まで動作する。
- 機能を増やしすぎず、目的達成に直結するMVPを完成させる。

#### ユーザビリティ

- 初見でも操作が分かる。
- 主要操作までの手数が少ない。
- 文字、ボタン、余白、色の視認性が高い。
- エラー時に原因と次の行動が分かる。
- スマートフォン幅でも崩れず操作できる。

#### 革新性

- 観光体験を改善する独自の切り口がある。
- 画期的なUI、デザイン、操作方法を、使いやすさを損なわず採用する。
- AIを要件整理、設計、実装、試験、文書化に活用した過程を説明できる。

#### 多様性

- 年代、性別等によらず利用しやすい。
- 色だけに依存しない情報表現にする。
- 十分なコントラスト、読みやすい文字サイズ、押しやすいボタンを確保する。
- キーボード操作、ラベル、代替テキスト等のアクセシビリティを考慮する。

### 9.2 テクニカル性

#### 正確性

- 主要機能が正常に動作する。
- 正常系だけでなく、空値、不正値、境界値、データなし、再読込も試験する。
- 起動手順が再現可能である。
- デモ直前の環境でも確実に起動できる。

#### セキュリティ性

- 入力値を検証する。
- 出力を適切にエスケープし、XSSを防止する。
- DBアクセスをパラメータ化し、SQLインジェクションを防止する。
- 不要なポート公開、デバッグモード、詳細エラー表示を避ける。
- パス・ファイル操作を制限し、パストラバーサルを防止する。
- 依存ライブラリを必要最小限にする。
- 秘密情報をソースへ埋め込まない。

#### データ完全性

- 入力制約とデータ型を定義する。
- 重複、欠損、不整合を防ぐ。
- 更新・削除時の挙動を明確にする。
- ローカル保存データの初期化・復元方法を用意する。
- サンプルデータで再現可能な状態にする。

#### 保守性

- 責務ごとにコードを分割する。
- 命名規則を統一する。
- 設定値とロジックを分離する。
- コメントは「何をしているか」より「なぜそうしたか」を記載する。
- READMEと設計書を実装に合わせて更新する。
- 将来の機能追加箇所が分かる構成にする。

## 10. AI生成コードの品質管理

AIは次を実施してからコードを提示すること。

1. 使用するパッケージが実在するか確認する。
2. 古い、非推奨、過剰な依存関係を避ける。
3. ライセンスと配布条件を明示する。
4. SQLインジェクション、XSS、パストラバーサル等のリスクを点検する。
5. コードの目的と重要な設計判断を説明する。
6. 実行コマンドと確認方法を提示する。
7. 正常系、異常系、境界値の試験を作成する。
8. 外部サービスなしで動作することを確認する。
9. Windows 11上のローカル環境で再現できるようにする。

人間側はAIの出力を鵜呑みにせず、コード、事実、依存関係、ライセンス、画面動作を確認する。

## 11. 推奨開発フロー

### フェーズ1: 要件確定

- 観光利用者の課題を1文で定義する。
- ターゲット利用者を定義する。
- 主要ユースケースを最大3件に絞る。
- 必須機能と余裕があれば実装する機能を分ける。
- 外部接続なしで成立するか確認する。

### フェーズ2: 設計

- 画面一覧と画面遷移を作る。
- データモデルを決める。
- アプリ構成とディレクトリ構成を決める。
- セキュリティ、ライセンス、アクセシビリティ方針を決める。
- 受入条件を定義する。

### フェーズ3: MVP実装

- まず主要ユースケースをエンドツーエンドで動かす。
- ローカル起動を確認する。
- 提供サンプルデータを読み込む。
- スマートフォン幅で主要操作を確認する。

### フェーズ4: 品質向上

- 入力検証、エラー処理、空状態を追加する。
- セキュリティ試験を行う。
- レスポンシブ表示とアクセシビリティを改善する。
- コードを整理し、不要な依存を削除する。

### フェーズ5: 成果物完成

- Markdown設計書を実装と一致させる。
- 試験結果を記録する。
- OSS・外部リソース・ライセンス一覧を完成させる。
- プレゼン資料を指定様式で作る。
- デモ手順と説明担当を決める。

### フェーズ6: 最終確認・提出

- クリーンな状態から起動できるか確認する。
- localhostで主要機能を再試験する。
- 外部接続を切っても動くか確認する。
- 機密情報、個人情報、認証情報を検索する。
- 指定フォルダと提出先を確認する。
- 締切直前を避け、余裕をもって提出する。

## 12. チーム運営

- PC操作者（オペレータ）を1人決める。
- 最大3名の役割例:
  - オペレータ兼実装担当
  - 要件・UX・データ担当
  - 試験・設計書・プレゼン担当
- 全員がAIへの指示、採用判断、レビューに参加する。
- 作業開始時に役割、優先順位、時間配分、撤退基準を決める。
- 共用Wi-Fiを占有する大容量ダウンロードを避ける。

## 13. Definition of Done

次をすべて満たした時点を完成とする。

- [ ] アプリが支給PC上のlocalhostで起動する
- [ ] スマートフォン・タブレット相当の画面幅で操作できる
- [ ] 主要ユースケースが最初から最後まで正常に動く
- [ ] 外部API、外部DB、クラウドへ実行時依存していない
- [ ] ログインなしで利用できる
- [ ] 提供テストデータまたは許可されたダミーデータを使用している
- [ ] 個人情報・機密情報・実在個人の識別情報を含まない
- [ ] APIキー、パスワード、トークン等を含まない
- [ ] XSS、SQLインジェクション等の基本対策を確認した
- [ ] 正常系・異常系・境界値の試験を実施した
- [ ] 設計書がMarkdown形式でソースと同じフォルダにある
- [ ] システム構成、画面、データ、機能、試験、起動方法が文書化されている
- [ ] OSS・ライブラリ・外部リソースとライセンスを一覧化した
- [ ] ソースが読みやすく、機能追加しやすい構成になっている
- [ ] 指定様式のプレゼン資料が完成している
- [ ] 提出先・提出方法・期限を確認した
- [ ] デモ手順を通しで確認した

## 14. AIへの初回プロンプト例

以下をAIへ渡し、本書と一緒に使用する。

```text
添付の「AI駆動開発競技 実装ガイド兼AI指示書」を最上位の制約として扱ってください。

これから観光利用者向けのローカルWebアプリを開発します。まずコードを書かず、次を順番に提案してください。

1. ターゲット利用者と解決する観光課題
2. アプリのコンセプト候補を3案
3. 各案の主要ユースケース、独自性、実装難易度、競技評価観点への適合
4. 外部API・クラウドなしで実現する方法
5. 限られた競技時間で完成可能なMVP範囲
6. 推奨案と選定理由
7. 画面一覧、画面遷移、データモデル
8. セキュリティ、アクセシビリティ、ライセンス上の注意
9. 実装・試験・文書化・プレゼンまでの作業順序

存在しないパッケージや外部サービスを提案しないでください。実行時はlocalhostで完結させ、外部API、外部DB、クラウドへ依存させないでください。
```

## 15. AIへの継続指示テンプレート

各タスクで次の形式を使う。

```text
目的:
今回完成させる機能を記載する。

前提:
- Windows 11
- localhostで動作
- 外部API、外部DB、クラウドは禁止
- スマートフォン・タブレット向け
- 認証機能は不要

入力:
使用する提供データ、既存ファイル、現在のコード構成を記載する。

受入条件:
- 正常系の期待結果
- 異常系の期待結果
- 境界値の期待結果
- レスポンシブ表示の期待結果
- セキュリティ上の期待結果

出力してほしいもの:
1. 方針
2. 変更対象ファイル
3. 実装コード
4. 実行・確認手順
5. 試験項目
6. セキュリティ・ライセンス・依存関係の確認結果
7. 設計書へ追記する内容
```
